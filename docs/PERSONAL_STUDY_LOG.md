# 개인 공부 기록 — 파일을 따라가며 정리하기

이 문서는 코드를 외우기 위한 정리가 아니라, **프로젝트를 처음부터 끝까지 직접 설명할 수 있도록 구현 의도와 핵심 개념을 파일 흐름에 맞춰 정리한 기록**입니다.

면접에서 함수 이름을 모두 기억하는 것보다 다음 질문에 답할 수 있는 것을 목표로 합니다.

```text
왜 이 단계가 필요한가?
이 단계가 없으면 어떤 문제가 생기는가?
어떤 데이터가 들어오고 어떤 데이터가 나가는가?
미래정보 누수는 어디에서 발생할 수 있는가?
이 결과를 어디까지 주장할 수 있는가?
```

전체 흐름은 다음과 같습니다.

```text
RUN_ME.bat
→ run_pipeline.py
→ src/collectors.py
→ src/sentiment.py
→ src/features.py
→ src/modeling.py
→ src/deep_research.py
→ src/deep_research_cached.py
→ src/move_research_cached.py
→ src/research_cache.py
→ src/reproducibility.py
→ reports/outputs
```

---

## 1. `RUN_ME.bat` — 실행 실수를 막는 입구

이 파일의 역할은 단순히 Python 파일을 실행하는 것이 아닙니다.

연구가 이미 잠긴 상태라면 기본적으로 다시 학습하지 않도록 막습니다. 미래 데이터를 본 뒤 같은 프로젝트에서 설정을 다시 바꾸면 미래 평가가 오염될 수 있기 때문입니다.

또한 `requirements.txt`의 hash를 비교해 패키지 목록이 바뀌지 않았다면 매번 설치를 반복하지 않습니다.

### 제가 이해해야 할 핵심

```text
연구 실행 자체도 통제 대상입니다.
실수로 재학습하거나 환경을 바꾸는 행동이 결과 재현성을 깨뜨릴 수 있습니다.
```

### 면접에서 설명한다면

> 연구가 끝난 뒤에는 실행 편의성보다 평가 오염을 막는 것이 더 중요하다고 생각했습니다. 그래서 기본 실행은 잠그고, 의도적으로 과거 연구를 재현할 때만 별도 환경변수를 설정하도록 만들었습니다.

## 2. `run_pipeline.py` — 전체 연구를 연결하는 오케스트레이터

이 파일은 모델 알고리즘을 구현하는 곳이 아니라 **어떤 연구 단계를 어떤 순서로 실행할지 관리하는 파일**입니다.

대략 다음 순서입니다.

```text
데이터 수집
→ 감성 데이터 처리
→ 피처 생성
→ 문제 정의와 모델 비교
→ 심화 탐색
→ 큰 움직임 전용 연구
→ 재현성 기록
```

각 단계마다 입력 파일, 소스 코드, 설정을 이용해 signature를 만듭니다.

이전 실행과 signature가 같고 결과 파일도 존재하면 해당 단계를 건너뜁니다.

### 왜 필요한가

실험이 많아질수록 매번 모든 단계를 다시 실행하면 시간이 많이 들고, 어느 결과가 어떤 코드에서 나왔는지 추적하기 어려워집니다.

### 면접에서 설명한다면

> 연구 단계를 하나의 긴 스크립트로 만들지 않고 단계별 checkpoint를 둔 이유는 실패 복구와 재현성 때문입니다. 데이터나 피처 코드가 바뀌지 않았다면 이후 실험에서 같은 계산을 반복하지 않도록 했습니다.

## 3. `src/collectors.py` — 서로 다른 시장 데이터를 하나의 시간축으로 모으기

이 파일은 다음 데이터를 수집합니다.

```text
BTC
ETH, BNB, XRP, SOL, ADA, DOGE, LTC
SPY, QQQ, Gold, DXY, VIX, TLT
Fear & Greed
Blockchain.com 온체인 지표
선택적으로 Coin Metrics, Glassnode
```

핵심은 단순히 API를 많이 연결한 것이 아닙니다.

각 데이터는 거래 시간과 갱신 주기가 다릅니다.

Bitcoin은 24시간 거래되지만 미국 증시는 주말에 휴장합니다. 온체인 지표와 심리 데이터도 발표 시점이 다를 수 있습니다.

따라서 수집 단계 이후에는 **그 값이 언제 실제로 알려졌는지**를 기준으로 다시 정렬해야 합니다.

### 제가 이해해야 할 핵심

```text
데이터의 날짜가 같다고 해서 같은 시점에 알고 있던 정보라는 뜻은 아닙니다.
```

이 원칙이 Point-in-Time 데이터 설계의 출발점입니다.

## 4. `src/sentiment.py` — 사용할 수 있는 것과 사용할 수 없는 것을 구분하기

X 게시글을 수집할 수 있는 경우 VADER 기반 감성 점수를 만들고 날짜별로 집계하는 기능이 있습니다.

다음 값을 만듭니다.

```text
게시글 수
평균 감성
중앙값 감성
긍정 비율
부정 비율
engagement
engagement 가중 감성
```

하지만 최종 연구에는 장기간의 역사 X 데이터가 충분하지 않았습니다.

그래서 기능이 구현되어 있다는 이유만으로 성능 실험에 사용했다고 주장하지 않습니다.

### 제가 배운 점

> 구현 가능 여부와 실제 실험에 포함되었는지는 구분해야 합니다.

면접에서도 "X 감성 파이프라인은 구현했지만 최종 잠금 성능에는 포함하지 않았다"고 정확히 설명해야 합니다.

## 5. `src/features.py` — 원시 가격을 시장 상태로 변환하기

이 파일은 모델이 바로 사용하기 어려운 원시 가격을 상대적인 시장 상태로 바꿉니다.

### BTC 자체 피처

```text
여러 기간의 수익률
로그수익률
rolling 평균과 변동성
하방 변동성
가격 z-score
거래량 z-score
EMA gap
RSI
MACD
Bollinger Band
drawdown
가격 범위 내 위치
```

가격 수준 자체보다 수익률이나 이동평균 대비 위치 같은 상대값을 많이 사용한 이유는 시간에 따라 BTC 가격 수준이 크게 달라졌기 때문입니다.

### Cross-Crypto 피처

다른 암호자산을 단순히 추가하는 것이 아니라 Bitcoin이 암호시장 전체와 비교해 어떤 상태인지 표현합니다.

```text
BTC - ETH 수익률
BTC - crypto basket 수익률
시장 상승 비율
rolling correlation
beta
residual return
```

예를 들어 `btc_crypto_residual_1d`는 암호시장 공통 움직임을 일부 제거한 뒤 Bitcoin 고유 움직임을 보려는 아이디어입니다.

### 거시시장 정렬

미국 시장의 휴장일은 미래 값으로 채우지 않고 마지막으로 알려진 값을 forward-fill합니다.

그 뒤 계산한 피처를 다시 1일 lag합니다.

```text
직전까지 알려진 값만 사용
→ 시장 피처 계산
→ 다시 1일 지연
```

`staleness_days`는 그 값이 마지막으로 갱신된 후 며칠이 지났는지를 나타냅니다.

### Target 생성

이 파일에서 `feature date`와 `target_end_date`를 별도로 만듭니다.

```text
feature date = 오늘
target_end_date = 다음 날
target_return_1d = 다음 날 종가 / 오늘 종가 - 1
```

이 구분이 이후 시간 누수 검사에서 매우 중요합니다.

## 6. `src/modeling.py` — 미래정보 누수를 코드에서 강제로 막기

이 파일에서 가장 중요한 부분은 모델 종류보다 시간 경계 검사입니다.

### 일반 random split을 쓰지 않은 이유

시계열에서는 미래 데이터가 train에 섞이면 실제 예측 상황과 달라집니다.

그래서 `TimeSeriesSplit`을 기반으로 과거에서 미래 방향으로만 나눕니다.

### `target_end_date`까지 검사하는 이유

예를 들어 9월 10일 입력의 정답이 9월 11일 수익률이면, 9월 10일 행 자체는 validation보다 앞에 있어도 정답 계산 시점은 validation과 겹칠 수 있습니다.

따라서 다음 조건을 모두 확인합니다.

```text
train 마지막 feature date < validation 시작
train 마지막 target_end_date < validation 시작
```

겹치는 train 행은 제거합니다.

### 제가 설명할 수 있어야 하는 질문

**Q. feature 날짜만 보면 안 되나요?**

아닙니다. label이 미래 수익률을 사용하므로 label이 참조하는 종료 시점까지 확인해야 합니다.

**Q. purge는 무엇인가요?**

validation 시작 이후의 정보를 정답 계산에 사용하게 되는 경계 train 행을 제거하는 과정입니다.

## 7. `src/deep_research.py` — 무엇을 예측할 것인지부터 비교하기

이 파일에서는 모델 하나의 성능만 올리는 대신 다음 요소를 연구 변수로 봅니다.

```text
학습 기간
라벨 정의
피처군
모델
문제 정의
분류와 회귀
```

### 문제 정의 비교

```text
3-class
DOWN / NEUTRAL / UP

Direction binary
UP / DOWN

Move binary
큰 움직임 없음 / 있음

Regression
다음 날 수익률 값 자체
```

이 비교에서 방향 binary는 ROC AUC가 약 0.513이었고, 회귀의 Pearson 상관도 거의 0이었습니다.

반면 move binary는 ROC AUC 약 0.714로 더 안정적인 신호를 보였습니다.

### 제가 배운 점

> 모델을 바꾸기 전에 문제 정의가 학습 가능한 형태인지 먼저 확인해야 합니다.

## 8. `src/deep_research_cached.py` — 전체 탐색을 무식하게 반복하지 않기

실험 공간이 커지면 가능한 모든 조합을 가장 비싼 CV로 돌리는 것이 비효율적입니다.

그래서 다음 방식을 사용했습니다.

```text
1차 빠른 탐색
→ 상위 후보만 선별
→ 더 많은 fold로 재검증
```

예를 들어 학습 window 5개를 빠르게 비교한 뒤 상위 후보만 더 엄격하게 확인합니다.

피처군도 먼저 한 모델로 넓게 비교하고 상위 피처군만 ExtraTrees, CatBoost, LightGBM으로 다시 검증합니다.

### 왜 이 방식이 필요한가

계산량을 줄이기 위한 목적도 있지만, 연구 질문을 단계적으로 좁히기 위한 목적도 있습니다.

다만 앞 단계에서 후보를 제거하기 때문에 완전한 exhaustive grid와 같지는 않습니다. 이 점도 한계로 설명해야 합니다.

## 9. `src/move_research_cached.py` — 최종적으로 살아남은 문제를 독립적으로 다시 연구하기

앞 단계에서 move binary가 상대적으로 강한 신호를 보였기 때문에, 기존 3-class 설정을 그대로 재사용하지 않고 move 문제만 다시 탐색했습니다.

다음 항목을 독립적으로 비교합니다.

```text
학습 window
변동성 window
k
피처군
모델
상위 피처 개수
decision threshold
```

최종 선택은 다음과 같았습니다.

```text
최근 730일
7일 변동성
k = 1.1
BTC + Crypto 피처군
ExtraTrees
Top 50 features
threshold = 0.50
```

### Threshold 검증

OOF 전체에서 threshold를 고르고 같은 데이터에 다시 점수를 계산하면 threshold도 과적합될 수 있습니다.

그래서 OOF를 시간순으로 나눴습니다.

```text
앞쪽 60% → threshold 선택
뒤쪽 40% → threshold 고정 검증
```

뒤쪽 432개 표본에서 Macro F1 0.6588, Balanced Accuracy 0.6861, ROC AUC 0.7239가 나왔습니다.

### 중요한 해석

이것도 실제 미래 데이터 결과는 아닙니다. 개발 데이터 안에서 threshold 선택과 검증을 시간상 분리한 것입니다.

## 10. `src/research_cache.py` — 같은 실험을 다시 학습하지 않기

캐시 key는 단순히 "ExtraTrees" 같은 모델 이름으로 만들지 않습니다.

```text
데이터 fingerprint
코드 fingerprint
피처 후보
모델 파라미터
학습 window
fold 수
Top K
라벨 설정
```

등을 함께 사용합니다.

같은 조건이면 이전 결과를 사용하고, 하나라도 바뀌면 새 실험으로 취급합니다.

### 원자적 저장

캐시 파일을 바로 덮어쓰지 않고 임시 파일에 쓴 뒤 교체합니다.

실행 도중 중단되었을 때 JSON이 반쯤 저장되는 문제를 줄이기 위한 방식입니다.

### 제가 배운 점

> 실험 관리도 연구 코드의 일부입니다. 계산 시간을 줄이는 것뿐 아니라 어떤 숫자가 어떤 설정에서 나왔는지 추적해야 합니다.

# 프로젝트를 면접에서 설명하는 흐름

## 30초 버전

> 학사 연구에서는 LSTM, GRU, Transformer로 Bitcoin 방향을 예측했습니다. 이후 코드를 다시 검토하면서 무작위 분할과 전처리 단계의 미래정보 누수 가능성을 발견했습니다. 그래서 현재 프로젝트에서는 point-in-time 데이터 정렬과 purged walk-forward validation을 적용하고, 방향 분류뿐 아니라 수익률 회귀와 큰 움직임 발생 여부까지 문제 정의를 비교했습니다. 방향 예측은 거의 랜덤 수준이었지만 큰 움직임 예측에서 상대적으로 안정적인 신호를 확인했고, 학습 기간, 외부시장 피처, 피처 수, threshold까지 시간순 개발 CV에서 검증한 뒤 설정을 잠갔습니다.

## 1분 버전에서 추가할 내용

> 데이터는 BTC뿐 아니라 주요 암호자산, SPY, QQQ, Gold, DXY, VIX, TLT, 온체인, Fear & Greed를 수집했습니다. 미국 시장 휴장일은 직전 관측값만 사용하고 다시 lag해서 미래정보 유입을 보수적으로 막았습니다. 각 validation fold에서는 feature 날짜뿐 아니라 label 계산에 사용한 target 종료일이 validation 시작 이전인지 확인하고 경계 표본을 purge했습니다. 또한 피처 선택도 train fold 안에서만 수행했습니다. 최종적으로 최근 730일, 7일 변동성의 1.1배 기준, BTC와 cross-crypto 피처, ExtraTrees, 상위 50개 피처가 선택되었습니다. 다만 이 결과를 실제 미래 성능으로 주장하지 않고 설정을 잠근 뒤 신규 데이터에서 검증하는 구조로 마무리했습니다.

# 마지막 정리

이 프로젝트에서 가장 크게 배운 것은 **시장 예측에서는 모델 구조보다 검증 설계가 먼저라는 점**입니다.

높은 성능 수치 하나보다 다음 질문을 계속 확인하는 것이 중요했습니다.

```text
이 정보는 당시 실제로 알 수 있었는가?
이 선택은 validation에서만 이루어졌는가?
특정 기간이나 seed에만 잘 맞은 것은 아닌가?
baseline보다 실제로 무엇이 좋아졌는가?
이미 본 결과를 다시 튜닝에 사용하고 있지는 않은가?
같은 실험을 다시 재현할 수 있는가?
```

이 질문들에 코드와 결과 파일로 답할 수 있도록 연구 구조를 설계했습니다.
